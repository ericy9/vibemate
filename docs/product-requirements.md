# VibeMate 产品需求文档

## 1. 产品定义

VibeMate 是一个帮助用户统一管理多个设备、运行环境和 AI 编码会话的桌面伙伴。
首批接入 Codex CLI 和 GitHub Copilot CLI。

当编码 Agent 出现以下情况时，VibeMate 应及时告知用户：

- 开始或继续执行任务；
- 需要权限或其他受支持的用户交互；
- 当前轮次执行完成；
- 执行失败或被中断。

对于受支持的权限请求，用户应能通过 VibeMate 选择 Allow 或 Deny，且决定必须
准确返回到发起请求的 Agent 会话。

当前审批范围仅包含 Codex，默认关闭，用户按环境主动开启。Copilot 使用原生审批，
VibeMate 通过 `notification/permission_prompt` 提醒用户回到终端；不把
`permissionRequest` 当作原生审批提示，因为它发生在 Allow All 和会话规则判断之前。

VibeMate 应提供三个共享同一聚合状态的数据消费界面：

- 统一管理面板，用于查看所有设备、Agent、任务、权限请求和连接健康状态；
- 可折叠的小型任务预览栏，用于持续查看全部活跃任务；
- 可隐藏的桌宠，用于表现用户选定关注范围内优先级最高的一个任务。

VibeMate 的长期定位不只是一款编码 Agent 监控工具。未来，同一个桌面伙伴还可以
提供喝水、久坐、休息和专注提醒。这些个人提醒必须与编码 Agent 集成层保持独立。

## 2. 目标用户与问题

首要目标用户会在 Windows 本机、一个或多个 WSL 发行版，或者独立 Linux 主机上
同时运行多个终端编码会话，并可能在 Agent 后台工作时切换去阅读或处理其他事情。
重要事件只出现在各自终端中，用户很容易错过任务完成或等待权限的提示。

VibeMate 应减少用户反复检查每个终端的需要，同时不能在用户不知情时替用户作出
涉及安全的决定。首次安装与日常配置必须面向不具备开发能力的用户；正常路径不得
要求用户使用终端、编辑 JSON、复制 Token，或者理解 IP、端口和 WebSocket。

### 2.1 Hook 安装与生命周期约束

- VibeMate 应通过配置向导自动完成 Hook 注册；用户只需明确确认授权，不应被要求
  手动编辑 Agent 配置文件。
- 生命周期采集与权限接管应提供独立选项。权限接管会在 Agent 原生权限提示前
  等待 VibeMate 决定，向导必须明确说明这一点。
- VibeMate 未启动、Receiver 不可用或程序异常退出时，Hook 必须快速返回无决定，
  让 Codex/Copilot 回到原生权限流程，不得造成长期阻塞。
- 卸载 VibeMate 时，应自动移除 VibeMate 自己注册的 Hook 和启动入口，同时保留
  用户已有配置，并提供备份与清理结果。
- Receiver、Hook runner 和安装器应随正式安装包交付，不应要求用户预先安装
  Node.js、克隆仓库或从源码构建 VibeMate。
- 上述约束属于产品必须满足的验收条件。

### 2.2 首次安装与环境接入

- Windows 用户应通过正式安装包完成桌面应用安装，安装完成后进入首次启动向导。
- 首次启动向导应自动检测 Windows 本机 Agent 和 WSL 发行版中的受支持 Agent，
  展示检测结果并在用户确认后安装 Receiver 与 Hook。
- 自动发现本身不得修改任何 Agent 配置；安装 Hook、部署 Receiver 和连接远程设备
  必须由用户明确确认。
- 本机 WSL 接入应自动完成 Receiver 部署、Hook 注册、启动、凭证引导和端到端连接
  测试。正常流程不得要求用户填写 WSL IP、端口或 Token。
- 自动扫描只读取 WSL 列表，不得启动已停止的发行版。用户可以明确选择启动并接入
  某个已停止的发行版。
- 独立 Linux 主机只通过用户从 GUI 明确选择已有 SSH 配置，或填写 SSH 主机信息后
  执行一键部署。第一版不支持没有 SSH 管理通道的 LAN-only 设备配对。
- VibeMate 可以只读发现已有 SSH 配置，但不得未经用户确认连接 SSH 主机、上传文件
  或修改远端配置。
- 手动主机地址、SSH 端口和认证配置只作为已有 SSH 配置之外的添加入口；Token、
  WebSocket 地址等底层传输参数不进入普通用户流程。
- 首次接入完成前，向导必须执行真实的状态上报和权限链路检查，并用面向用户的语言
  展示成功结果或可执行的修复操作。
- 后续启动、重连、兼容升级和修复应自动进行；无法自动修复时应提供 Doctor 诊断和
  一键修复，而不是只展示底层错误。
- 卸载时必须移除 VibeMate 管理的 Receiver、Hook 和设备凭证，同时
  保留用户与其他工具管理的配置。

### 2.3 Receiver 生命周期

- 只在用户确认启用的环境中安装 Receiver，不得因检测到环境就自动部署。
- Windows 本机 Receiver 跟随桌面应用运行；WSL Receiver 通过 `wsl.exe` 按需拉起；
  独立 Linux Receiver 通过已经确认的 SSH 配置按需拉起。
- 第一版不提供无人值守监控，也不要求 Receiver 作为系统开机服务永久运行。
- 桌面应用退出时，应并行、限时地请求所有由它启动的 Receiver 结束待处理权限并
  关闭。关闭失败不得长期阻塞桌面应用退出。
- Receiver 必须把桌面控制连接视为有时限的运行租约；桌面异常退出、网络中断或
  正常关闭未得到确认时，Receiver 应在短暂重连宽限期后自行退出。
- 普通退出中的单个 Receiver 停止失败应记录并在下次启动时自动清理或接管，不应向
  普通用户弹出底层进程错误。仍有待处理权限请求时，应提示退出会使请求回退到 Agent
  原生审批流程。

## 3. 产品原则

### 3.1 先完成 Agent 集成，再实现展示层

第一个里程碑是可靠地采集、归一化、存储和观察编码 Agent 事件。桌宠只是后续的
数据消费者，不属于事件采集层。

### 3.2 会话身份是基础能力

从第一个事件开始，就必须保存带设备、运行环境和 Agent 命名空间的会话
身份。一个终端的权限决定绝不能返回到另一个终端、WSL 发行版或 Linux 主机。

同一个 WSL 发行版中的一个 Receiver 必须能够同时追踪多个 Codex/Copilot 进程和
会话。多个 WSL 发行版或独立 Linux 主机分别运行 Receiver，由桌面端统一聚合。

### 3.3 权限处理失败时回退 Agent 原生流程

如果 VibeMate 未运行、被禁用、等待超时、失去请求连接，或者无法证明请求归属，
就必须返回“无决定”，让 Codex 或 Copilot 使用自己的原生权限流程。

集成故障不能被转换为自动 Allow，也不能被转换为自动 Deny。

### 3.4 只采集必要信息

VibeMate 不应持久化完整提示词、文件内容、命令输出、访问令牌、密钥或未受限制的
工具输入。只采集满足状态展示、问题诊断和权限判断所需的、经过清理且长度受限的
元数据。

### 3.5 展示层分工明确

- 设置页负责设备与环境的添加、修复、启停和偏好，不展示任务列表。
- 悬浮监控窗是日常主界面：常态为一枚只含数量的胶囊，点击展开为精简任务列表，
  展示所有活跃、等待处理和最近完成的任务，可独立于桌宠显示。
- 悬浮监控窗出现待处理项时只改变颜色提示，不自动展开打断用户。
- 桌宠一次只表达一个主要任务状态，不承担完整多任务列表职责。
- 桌宠的“关注范围”可设为所有设备、指定设备、指定项目或指定会话。在所选范围内，
  按等待权限、失败、等待输入、完成、工作、空闲的优先级选择主要任务；同优先级时
  优先最近活动的任务。
- 即使桌宠固定关注某个范围，其他范围的权限请求或严重错误也必须通过角标、预览栏
  或系统通知提示，不得静默遗漏。
- 用户可以选择“桌宠和预览栏”“仅桌宠”“仅预览栏”或“全部隐藏，仅保留托盘与
  系统通知”。

## 4. 第一阶段：编码端信息采集

### 4.1 支持的 Agent

- Codex CLI
- GitHub Copilot CLI

首先验证本地集成。只有在协议端到端运行稳定后，再逐步增加其他平台和远端设备。

### 4.2 统一状态

不同 Agent 的原始事件应归一化为一套小而稳定的状态：

| 统一状态 | 含义 |
| --- | --- |
| `idle` | 会话存在，但当前没有处理任务 |
| `thinking` | 用户已提交请求，Agent 正在规划 |
| `working` | Agent 正在调用工具或执行实际工作 |
| `waiting_permission` | 有权限请求正在等待用户决定 |
| `completed` | 当前轮次已完成 |
| `failed` | 当前轮次或工具执行失败 |
| `ended` | Agent 提供会话结束事件时，表示会话已结束 |

系统还应保留有长度上限的原始事件诊断记录，以便调查错误映射，但不能因此扩大共享
状态集合，也不能记录敏感原始载荷。

### 4.3 统一事件结构

第一版协议建议包含以下字段：

```json
{
  "protocolVersion": 1,
  "eventId": "unique-event-id",
  "agent": "codex",
  "sessionId": "agent-session-id",
  "state": "working",
  "event": "PreToolUse",
  "occurredAt": "2026-08-13T12:00:00.000Z",
  "cwd": "/path/to/project",
  "tool": {
    "name": "shell",
    "summary": "bounded sanitized summary"
  },
  "process": {
    "sourcePid": 1234
  }
}
```

Agent 无法提供的字段可以省略。内部会话键必须至少包含设备、运行环境、Agent、
`sessionId`，避免两个 Agent、环境或设备使用相同的原始
`sessionId` 时发生冲突。

### 4.4 普通状态事件流程

生命周期事件是单向、非阻塞的：

```text
Agent Hook -> 本地接收服务 -> 归一化 -> 会话存储 -> 开发观察器
```

Hook 失败不能阻塞 Agent。重复的完成信号必须去重，保证一个执行轮次最多产生一次
面向用户的完成事件。

### 4.5 权限事件流程

权限请求是双向的。它只在 Agent Hook 允许的有限时间内阻塞：

```text
Agent 权限 Hook
  -> 本地接收服务
  -> 待处理权限存储
  -> 开发用决策界面
  -> Allow / Deny / 无决定
  -> 准确返回给等待中的 Hook
```

每个待处理权限请求都必须拥有唯一的请求 ID，并至少绑定：

- Agent 类型；
- 会话 ID；
- 工具名称；
- 经过清理的工具输入或操作摘要；
- 当前等待中的响应连接；
- 创建时间和过期时间；
- 最终决定状态。

每个请求只能有一个最终决定。迟到、重复、过期或身份不匹配的响应必须被拒绝。

### 4.6 开发观察器

第一阶段先实现开发观察器，而不是桌宠。它可以是终端界面或一个只在本机打开的
简单网页，但必须能够：

- 按 Agent 和会话显示实时统一事件；
- 显示用于诊断的原始事件名称；
- 列出正在等待的权限请求；
- 在受控测试中提交 Allow 或 Deny；
- 显示超时、格式错误、事件去重和原生回退结果。

### 4.7 第一阶段验收标准

- 同时运行两个或更多终端时，会话不会互相覆盖，事件不会串线。
- Codex 生命周期事件能映射到统一协议。
- Copilot 生命周期事件能映射到同一套协议。
- Codex 主动开启审批后可完成 Allow 和 Deny 闭环；关闭时立即回退原生流程。
- Copilot 不进入桌面审批队列，真实权限提示只触发提醒，保留原生授权行为。
- 权限决定始终返回到准确的 Agent、会话和请求。
- 服务关闭、等待超时或数据格式错误时，会回退到 Agent 原生审批流程。
- 一个执行轮次最多生成一次统一的完成事件。
- 日志和持久化数据不包含已知敏感载荷。
- 协议校验、事件映射、会话路由、超时和去重均有自动化测试。
- 同一 Receiver 下同时运行多个 Codex/Copilot 任务时，状态和权限请求可以独立追踪。

## 5. 后续阶段需求

### 第二阶段：安装、配置与桌面伙伴

- Windows x64/ARM64 正式安装包、自动更新和完整卸载清理
- 面向非开发者的首次启动向导
- Windows 本机与默认 WSL 环境自动检测
- 用户确认后的一键 Receiver/Hook 部署、连接测试和一键修复
- Electron 应用外壳和托盘生命周期
- Clawd 风格的像素桌宠，使用前需确认代码和素材许可证
- 空闲、思考、工作、等待权限、完成和失败动画
- 桌宠旁的权限气泡，提供 Allow 和 Deny
- 声音和系统原生通知

### 第三阶段：统一面板与多任务体验

- 汇总全部已连接 Receiver 的统一管理面板
- 可折叠且可独立显示的小型任务预览栏
- 桌宠关注范围和显示模式设置
- 未读完成事件和待处理权限标记
- 会话别名与项目名称
- 按设备、运行环境、Agent、项目和状态筛选
- 尽力切换到匹配的本地终端
- 多 Receiver 连接管理、独立重连、凭证和版本兼容状态
- 断线时保留最后快照并明确标记过期，禁止向断线设备提交权限决定

### 第四阶段：更多环境与远程 Agent

- 多 WSL 发行版检测和接入
- 从已有 SSH 配置发现主机，以及 GUI 手动添加 SSH 主机
- 通过 SSH 一键部署、更新和卸载 Receiver/Hook
- 独立 Linux 安装包，以及树莓派和其他 Linux 主机支持
- 按远端配置隔离路由，避免远端会话 ID 冲突
- 明确展示远端连接健康状态
- 远端状态与权限请求传输

### 第五阶段：个人提醒

- 喝水提醒
- 久坐和休息提醒
- 专注计时器
- 免打扰时段和提醒计划
- 提醒专用的桌宠动画和声音

## 6. 初始版本不做的内容

- Claude Code 和其他编码 Agent
- 自动批准权限的策略
- 手机客户端和聊天平台审批
- 云端同步
- 多只桌宠或每个终端一只桌宠
- 公共插件或主题市场
- 未经用户确认自动连接 SSH 主机或修改远端 Agent 配置
- 没有 SSH 管理通道的 LAN-only 设备配对
- Receiver 无人值守监控和系统开机永久常驻

## 7. 许可证要求

从参考项目复制源代码、名称、声音或视觉素材前，必须检查其软件许可证及可能独立
存在的素材授权条款，并保留所有必要的版权和许可证声明。

规划阶段可以参考其架构，但不能默认所有美术素材、声音和品牌元素都允许复用。
